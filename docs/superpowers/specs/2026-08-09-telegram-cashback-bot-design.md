# Telegram-бот распознавания кешбэка — Дизайн (MVP)

- **Дата:** 2026-08-09
- **Статус:** Draft (согласован устно, ожидает ревью → план реализации)
- **Автор:** skuze + Claude (brainstorming)
- **Связанные:** `docs/superpowers/specs/2026-08-09-fix-cashback-recognition-design.md` (Подход 1 уже сделан)

## 1. Контекст и проблема

Первые 5 тестовых клиентов. Один отказался заполнять сервис вручную и написал собственный GPT-промт: скидывает скриншоты кешбэка → GPT распознаёт → отвечает «какой картой платить». Сигнал: **пользователю не нужен «сервис учёта», ему нужен ответ с минимумом действий**.

В проекте уже есть инфраструктура, которую другая ИИ описывала «с нуля»:
- `AiService::recognizeGigaChat()` уже делает «скриншот → GigaChat vision → JSON `[{category, cashback}]` → fuzzy-маппинг в категории пользователя → `card->cashback_json`» (веб-контекст одной карты).
- `Category` с `keywords`, `SearchComponent` (Livewire) — поиск по категории.
- GigaChat подключён (токен в env, кэш, refresh на 401).

**Цель:** дать тот же UX «скинул скрин → получил результат» через **Telegram-бота**, переиспользуя существующий бэкенд. Веб остаётся источником правды.

## 2. Scope

### В scope (MVP)
- Telegram-бот: `/start`, привязка к аккаунту LaraCash, меню.
- Сценарий «обновить кешбэк»: выбор карты → приём фото → распознавание → отчёт (saved/skipped) → применение в pivot с подтверждением.

### Вне scope (отдельные spec'и)
- Запрос естественным языком «аптека 3500 → лучшая карта» (следующая итерация; чистый PHP, без LLM).
- Расчёт в рублях с учётом лимитов/MCC.
- Ежемесячные напоминания, история кешбэка по месяцам, снапшоты.
- MAX-бот (max.ru) — другой мессенджер; проектируем расширяемо, не реализуем.
- Удаление/починка мёртвых фич (`all_available_cashback`, роуты-зомби) — отдельная задача.

## 3. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Интерфейс | Telegram-бот (диалог: текст + фото). MAX-бот позже. |
| Текущий веб | Источник правды; бот — потребитель поверх той же БД. |
| MVP | Только распознавание скринов. |
| Привязка аккаунта | Из бота ссылка с `telegram_id` → ЛК → авторизация → сохранение `users.telegram_id`. |
| Карта из скрина | Бот спрашивает (inline-клавиатура карт юзера). |
| Категории | Маппинг на существующие категории юзера (как сейчас) + отчёт о нераспознанных. |
| Применение в pivot | С подтверждением юзера («применить в таблицу?»). |
| Транспорт | **A:** Webhook на проде + polling для локалки (флаг), голый HTTP, переиспользование `AiService`. |

## 4. Архитектура

Слои, изолированные по принципу «доменная логика не зависит от транспорта TG» (для будущего MAX).

| Слой | Компонент | Зависит от TG? |
|---|---|---|
| Transport | `TelegramBotService` (raw `Http`: sendMessage, inline-keyboards, приём photo), `TelegramWebhookController`, `TelegramPollCommand` | Да, изолирован |
| Conversation | `BotConversationService` — state-machine по `telegram_id` | Нет |
| Domain | `CashbackImportService` — фото → распознать → сравнить → `{saved, skipped}` → применить | Нет (переиспользуется MAX) |
| AI | `AiService::recognize($userId, $fileSource)` — рефактор, отвязан от `auth()->user()` | Нет |
| Data | pivot `Cashback` = источник правды; `card.cashback_json` = буфер; `users.telegram_id` = связь | Нет |

### 4.1. Источник правды кешбэка (установлено исследованием)
- **pivot `card_category_cashback` (модель `Cashback`)** — источник правды для отображения/расчёта.
- **`card.cashback_json`** — буфер распознавания; в вебе переносится в pivot кнопкой `fill_recognize`.
- Следствие: **бот обязан писать в pivot** (иначе веб не увидит, расчёт пойдёт мимо). Буфер `cashback_json` используется как промежуточное звено и для отчёта.

## 5. Компоненты

### Новые
- `app/Services/Telegram/TelegramBotService.php` — raw HTTP к TG Bot API (отправка сообщений/клавиатур, разбор `update`).
- `app/Http/Controllers/TelegramWebhookController.php` + роут `POST /telegram/webhook` (секретный токен в URL/header).
- `app/Console/Commands/TelegramPollCommand.php` — `getUpdates` в цикле для локалки (запускается флагом/окружением).
- `app/Services/Bot/BotConversationService.php` — состояния диалога; хранит state по `telegram_id` (cache для MVP).
- `app/Services/CashbackImportService.php` — оркестрация: скачать фото → `AiService::recognize($userId, $photo)` → сравнить с категориями юзера → вернуть `{saved, skipped}` → применить в pivot по подтверждению.
- migration `add_telegram_id_to_users` (nullable string/unsigned bigint, уникальный).
- Веб-ЛК: кнопка «Привязать бота» + контроллер `BotLinkController@store` (только под `auth`, сохраняет `telegram_id` из query).

### Изменяемые (точечно, не переписываем)
- `app/Services/AiService.php`:
  - `getPrompt($userId)` вместо чтения `auth()->user()->id`.
  - `recognize($userId, $fileSource)` — принимает источник файла (путь в storage ИЛИ бинарный контент/временный путь фото из TG), а не `Card` + `auth()`. Существующий `getRecognizedCashback(Card)` становится тонкой обёрткой: `recognize($card->user_id, storage_path(...))`.
  - `downloadFile` обобщается: загрузка произвольного файлового источника в GigaChat.
- `config/services.php` + `.env.example`: секция `telegram.bot_token`.

## 6. Поток данных

### S1. Привязка аккаунта (безопасная)
1. Юзер `/start` в боте → бот ищет `User` по `telegram_id` (из update).
2. Не найден → бот: «Привяжи аккаунт LaraCash» + кнопка/ссылка `laracash.dev/bot/link?tg=<telegram_id>`.
3. Юзер открывает ссылку → middleware `auth` → если не залогинен, форма логина → после логина `BotLinkController` сохраняет `auth()->user()->telegram_id = <tg>`.
4. Юзер возвращается в бот → `/start` → бот: «Привязан к <user>. Карт: N».

> `telegram_id` в ссылке не секрет — привязка выполняется только под сессией владельца аккаунта. Дубликат `telegram_id` у другого user → ошибка/перепривязка (уточняется в плане).

### S2. Распознавание кешбэка (главный сценарий MVP)
1. `/start` → меню: «Обновить кешбэк», (заглушки «Проверить покупку», «Мои карты» — вне MVP).
2. «Обновить кешбэк» → бот: inline-клавиатура карт юзера (`Card::where('user_id', ...)`). Если карт 0 → «сначала добавь карту в ЛК».
3. Юзер выбирает карту → state `await_photo`.
4. Юзер шлёт 1..N фото → `CashbackImportService::import($userId, $cardId, $photos)`:
   - скачать каждое фото во временный файл;
   - `AiService::recognize($userId, $photo)` → JSON `[{category, cashback}]`;
   - сравнить `category` с категориями юзера (`matchCategory`, как сейчас): совпавшие → `saved`, остальные → `skipped`;
   - вернуть `{ saved: [{title, percent}], skipped: [str], card_id }`.
5. Бот: отчёт «✅ Сохраню: Аптеки 5%, Кафе 3%. ⚠️ Нет в ЛК: ЖД билеты, Каршеринг — добавь в ЛК, чтобы учитывать» + кнопки «Применить» / «Отмена».
6. «Применить» → `CashbackImportService::apply($userId, $cardId, $saved)`: writes `cashback_json` (буфер) + обновляет pivot `Cashback` (`updateOrCreate` по card+category). Бот: «Готово».
7. «Отмена» → ничего не пишется, state → idle.

### S3. Запрос «какая карта» — ВНЕ MVP (следующий spec)
Чистый PHP: категория + сумма → pivot → расчёт → лучшая карта. Без LLM.

## 7. Обработка ошибок
- Не привязан → бот направляет ссылкой в ЛК (S1).
- GigaChat: пустой/невалидный ответ → «не распозналось; приложи скрин чётче и/или добавь недостающие категории в ЛК». Фото не теряет state, можно повторить.
- Таймаут GigaChat (90s, как сейчас) → ответ-заглушка, диалог не виснет, state сбрасывается в idle.
- Несколько фото в одном сообщении → обрабатываются последовательно, отчёт общий по карте.
- Несоответствие фото/выбор карты (например фото пришло до выбора карты) → «сначала выбери карту».
- Стоимость: **LLM только на распознавание** (1 скрин = 1 вызов); повторных вызовов на скрин нет. Запросы покупки (вне MVP) — 0 токенов.

  - `AiService::recognize($userId, $fileSource)` — отвязанный от `auth()` (mock `Http`, как в существующих тестах `AiServiceTest`).
  - Привязка: `BotLinkController` сохраняет `telegram_id` только под `auth`; дубликат-кейс.
- **Feature:**
  - `TelegramWebhookController` — `/start` (привязан/не привязан), приём фото, inline-кнопки.
  - Переходы `BotConversationService` между состояниями.
- Тесты — через агента `laravel-test-generator` (по правилам проекта).

## 9. Открытые риски и предположения (проверить в плане)

1. **Применение в pivot и техдолг.** Существующий `updateOrCreate` пишет `cashback_percentage = 0` вместо DELETE при пустом проценте; истории по месяцам нет. Авто/ручное применение может затереть правки лимитов/MCC. Смягчение: применяем **с подтверждением** (выбрано); в плане — проверить, не затирает ли `apply` существующие ненулевые записи и не плодит ли нули.
2. **Точность распознавания на реальных скринах через бота.** GigaChat на мобильных скринах не валидирован в бот-режиме. Если точность низкая — UX «скинул → готово» разваливается (это отложенный фолбэк «Подход 3» из памяти). В плане: пробный прогон на реальных скринах 2–3 банков перед основной работой.
3. **Webhook на проде.** Требует публичного HTTPS-домена + регистрацию webhook у TG. Если хостинг не даёт публичного HTTPS — откат к polling (B). Проверить возможности хостинга на этапе плана.
4. **Двойная запись кешбэка.** `cashback_json` (буфер) + pivot — два места. Убедиться, что `apply` делает их консистентными и что веб-форма `fill_recognize` и бот не конфликтуют.

## 10. Data model changes
- `users.telegram_id` (nullable, unique) — migration `add_telegram_id_to_users`.
- Других изменений схемы нет. Pivot `Cashback` и `cashback_json` используются как есть.

## 11. Влияние на существующий код
- `AiService`: рефактор сигнатур (отвязка от `auth()`), поведение для веба сохраняется через обёртку. Существующие 11 юнит-тестов должны оставаться зелёными (возможно, адаптация вызовов).
- Веб-формы карт/кешбэка: без изменений (источник правды).
- Новые роуты: `/telegram/webhook`, `/bot/link` (+store). Не конфликтуют с мёртвыми роутами-зомби (те — отдельная задача).
